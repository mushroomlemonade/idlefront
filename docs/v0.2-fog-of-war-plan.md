# v0.2 — Discovery and scalable worlds

Status: approved plan; implementation in progress. Not a release announcement.

## Intended experience

Begin with animated pixel clouds tight against the starting border. When wilderness expansion ends, reveal neighbouring territories and their fronts, without recursively revealing their neighbours. Growth, structures and diplomacy gradually open the world; late-game visibility can become nearly global. Exact growth thresholds need playtesting, not invented balance changes.

Factories reveal their existing connection radius. Moving trains and transports provide local sight; warships scout farther. Trade ships do not directly scout, but their visible routes intentionally offer clues about hidden geography. Charted terrain persists; live enemy intelligence requires current sight. Alliance visibility includes allied fronts and industry, without granting recursive enemy intelligence.

## Delivery order

1. **Visibility foundation:** sparse, incremental coverage with overlapping sources, persistent exploration, and bounded dirty-region updates. Separate live sight, charted terrain, and simulation activity.
2. **Native visual prototype:** world-anchored WebGL pixel clouds, restrained animation, dithered shading, readable edges and smooth reveals. Inspect screenshots at mobile and desktop sizes before integration; real-device review remains a release gate.
3. **Authoritative integration:** derive sources from the simulation. Filter snapshots, updates, unit paths, hover/query data and commands on the server. Hidden entities must be removed from client caches when sight is lost. Audit indirect information through names, events, diplomacy and totals; preserve only deliberately public information.
4. **Reconnect and persistence:** key exploration by stable match/player identity, never IP or device. Restore exploration and recalculate live sight before sending the first board snapshot. Cover device switching, catch-up, server recovery, and alliance/source changes while offline. Never briefly show the unrestricted board.
5. **Simulation savings:** explicitly approximate isolated remote bot-only activity. Do not merely batch full-cost ticks. Human nations, including offline humans, allied fronts and incoming interactions stay full fidelity. Wake regions before ships, trains, attacks or scouting reach them. Visibility alone is not a sufficient activity test.
6. **Release gate:** representative 27x and larger-map profiling, mature-world workloads, reconnect tests, visual review and a real multi-device playtest before calling v0.2 ready.

## Engineering constraints

- No full-map or per-player full-world scan each frame/tick. Recompute affected coverage when sources or relevant state change; animate independently on the GPU.
- Use compact, lazy pages and merged source spans. Update only old/new footprint differences; overlapping sources must survive another source leaving.
- Coarse visual fog may smooth edges, but must never grant access to hidden authoritative information.
- Exploration checkpoints need versioning, validation and deterministic recovery. Current visibility is recalculated, not trusted from stale client state.
- Bound incoming snapshot work so mobile clients remain responsive. Audit motion plans that cross hidden space.
- Factory connection mechanics and normal combat/economy remain unchanged except the explicitly approved approximation of isolated bot-only simulation. No unrequested pacing changes.
- Keep unfinished behavior gated; do not label a visual demo as authoritative fog or a measured simulation speedup.

## Acceptance checks

- Tight spawn sight, expansion transition, neighbour non-recursion, industrial scouting and alliance revocation.
- Overlapping and moving sources, map edges, exploration without stale enemy intelligence.
- Two devices viewing one player agree; separate players behind one IP remain separate.
- Join/rejoin/recovery never leak the full map's live state, including during catch-up.
- Remote bots resume coherently before contact, without visible jumps or throttling humans.
- Record CPU time, TPS, memory, network bytes and client frame time against the same baseline/workloads. Set release budgets from those measurements, not promises.

## Integration findings and remaining risks

- **Pending user decision:** spectator policy. Asked whether spectators should choose a participant's fog perspective (recommended), see a delayed whole map, or be disabled. No answer yet. Non-participant fog streams currently fail closed; unrestricted live spectating must not bypass fog.
- Live Firefox walkthrough needs app approval; iOS/Expo and Mac GPU behavior need real-device testing. Do not announce the release as finished based only on headless tests/screenshots.
- Long-duration/mature fleets, 12 viewers, large alliance reveals, combat-edge activation and worst-case whole-map discovery still need dedicated soak/load tests. Current reports are short headless workloads, not weeks-long certification.
- Fog reconnect currently requests a fresh page/snapshot instead of replaying a visibility-sensitive partial history. Correctness is covered, but a seamless in-place resnapshot/reset is still a UX improvement to implement and validate.
- Player exploration is reconstructed from the journal on server recovery. Separate durable simulation/checkpoint acceleration remains future work; a week-long journal must not be mistaken for a cheap recovery path.
- Bot scheduling is deliberately limited to remote land expansion. It is not a regional multi-threaded simulation or a 1-Hz economy/vehicle engine. Core attack/BFS/frontier costs still dominate fully active areas; larger late-game worlds will need further exact optimizations.
- The preview is not pushed or deployed to production and the application release version is not bumped to v0.2 yet.
